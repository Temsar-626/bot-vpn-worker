# راه‌اندازی BPB (پنل روی Cloudflare Worker)

این ماژول برای هر اکانت Cloudflare دقیقاً **یک Worker از BPB-Worker-Panel** می‌سازد
(منطق نصب مشابه [BPB-Wizard](https://github.com/bia-pain-bache/BPB-Wizard)):
verify توکن → ساخت KV → دانلود `worker.js` رسمی → embed تنظیمات → دیپلوی → فعال‌سازی ساب‌دامین.

## ۱) پیش‌نیازها

- توکن Cloudflare هر فروش با دسترسی: **Edit Workers** + خواندن **Account Settings** + **KV**
  (برای تخمین مصرف روزانه، دسترسی خواندن Analytics هم لازم است؛ بدون آن تخمین مخفی می‌ماند).
- سکرت `VAULT_KEY` **اختیاری** است: اگر ست باشد توکن‌ها رمزنگاری‌شده ذخیره می‌شوند،
  وگرنه plaintext. در هر صورت توکن خام در لاگ، API لیست و UI برنمی‌گردد (فقط ماسک یا با دکمه نمایش).
  ⚠️ بدون `VAULT_KEY` هرکس به دیتابیس/بکاپ دسترسی داشته باشد توکن‌ها را می‌بیند — دسترسی ادمین را محدود نگه دارید.
- هرگز توکن خام (`ghp_` یا CF API Token) را در کد، `wrangler.toml` یا کامیت نگذارید.

## ۲) افزودن اکانت

۱. پنل ادمین → تب مستقل **BPB** (کنار «سرویس / VPN») → «اکانت جدید» (label + API Token).
۲. دکمه **نصب**: سیستم توکن را verify می‌کند، KV می‌سازد، آخرین `worker.js`
   ([دانلود رسمی](https://github.com/bia-pain-bache/BPB-Worker-Panel/releases/latest/download/worker.js))
   را می‌گیرد و یک Worker دیپلوی می‌کند. وضعیت `free` یعنی آماده فروش.
۳. قانون: هر اکانت CF فقط یک Worker. نصب دوم روی همان اکانت با خطای `already_claimed` رد می‌شود.

### مدیریت در مقیاس بالا

تب BPB برای چندصد اکانت طراحی شده: جستجو (نام/ایمیل/ورکر)، فیلتر وضعیت (کلیک روی
کارت‌های آمار هم فیلتر می‌کند)، مرتب‌سازی (آخرین تغییر، نام، نزدیک‌ترین انقضا)،
صفحه‌بندی ۲۵/۵۰/۱۰۰تایی، انتخاب با چک‌باکس (تکی، صفحه، یا همه نتایج فیلتر)،
عملیات گروهی نصب/قطع دسترسی/تنظیمات/حذف با نوار پیشرفت و امکان انصراف، و خروجی CSV
(بدون سکرت). اسلات‌هایی که تا ۳ روز آینده منقضی می‌شوند هشدار دارند.

## ۳) فروش

۱. در تب **پنل‌ها** یک پنل از نوع **BPB (Cloudflare Workers)** بسازید (URL/credentials لازم نیست؛ فقط عنوان/ظرفیت).
۲. پلن را به آن پنل وصل کنید (مثلاً ۱۵۰ گیگ / ۳۰ روزه). خرید موفق، قدیمی‌ترین اسلات `free` را `sold` می‌کند،
   `expire_at` می‌گذارد و فقط **لینک مستقیم ورکر** را در تلگرام می‌دهد (پیام تحویل اختصاصی BPB با تاریخ انقضا).
۳. موجودی = تعداد اسلات‌های `free`؛ پلن‌هایی که اسلات آزاد ندارند خودکار از ویترین ربات پنهان می‌شوند و روی دکمه پلن، موجودی زنده نمایش داده می‌شود.
۴. نکته صادقانه فنی: خود ورکر BPB سقف حجمی لحظه‌ای اعمال نمی‌کند؛ «۵ گیگ در روز / ۱۵۰ گیگ» سیاست مصرف منصفانه است و قطع دسترسی سر تاریخ انقضا انجام می‌شود. این متن را در توضیحات پلن بنویسید.

## ۴) انقضا، لغو و بازگشت وجه

کرون هر دقیقه (`* * * * *`) اسلات‌های `sold` با `expire_at` گذشته را با **چرخاندن
securePath + UUID ولیس / پسورد Trojan و redeploy** باطل می‌کند و اسلات را `free` می‌کند.
سرویس linked هم در `sync` بعدی `expired` می‌شود.

لغو توسط کاربر — بدون نیاز به تأیید ادمین — هم در ربات (دکمه «لغو و بازگشت وجه» روی سرویس)
و هم در مینی‌اپ (مدیریت سرویس → «لغو فوری و استرداد») با همان منطق کار می‌کند:
۱. پیش‌فاکتور pro-rata نشان داده می‌شود: `پرداختی × روزهای کامل باقی‌مانده / روزهای کل`.
   روز جاری همیشه کسر می‌شود (مثلاً لغو نیم ساعت بعد از خرید ۳۰ روزه ۱۵۰هزار تومانی → ۱۴۵هزار تومان).
۲. با تأیید، مبلغ فوراً به **کیف پول** برمی‌گردد، سرویس بسته می‌شود و اسلات به مسیر انقضا سپرده می‌شود (لینک حداکثر تا یک دقیقه بعد می‌میرد).
۳. درخواست refund دستی هم همان منطق را دارد؛ در پنل ادمین مبلغ پیشنهادی pro-rata از قبل محاسبه و نمایش داده می‌شود (قابل ویرایش توسط ادمین).

## ۵) مصرف روزانه (تخمینی، از Analytics کلادفلر)

پلن ورکرهای رایگان کلادفلر سقف **۱۰۰هزار ریکوئست در روز** دارد. سیستم تعداد ریکوئست
۲۴ ساعت گذشته هر ورکر را از GraphQL Analytics می‌خواند و به نسبت روی سقف روزانه
پلن می‌نگارد (مثلاً ۵۰هزار ریکوئست از ۱۵۰گیگ/۳۰روز = حدود ۲٫۵ گیگ از ۵ گیگ روزانه).
نتیجه در ربات (صفحه سرویس) و مینی‌اپ نمایش داده می‌شود.

- این عدد **تخمینی** است (ریکوئست ≠ بایت) و فقط راهنماست؛ قطع دسترسی همچنان سر انقضاست.
- خواندن Analytics بهترین‌تلاش است: با کش ۳۰ دقیقه‌ای، بدون کند کردن sync/خرید، و در صورت
  خطا (مثلاً دسترسی ناکافی توکن) بی‌صدا مخفی می‌ماند. اگر تخمین را نمی‌بینید، به توکن CF
  دسترسی خواندن Analytics هم بدهید.
- خریدار هیچ‌جا کلمه BPB نمی‌بیند: پیام تحویل و صفحه‌ها عمومی‌اند (نام و لوکیشن همان است که ادمین روی پنل/پلن گذاشته).

## ۵) تنظیمات پیش‌فرض نصب و پسورد پنل

- تب BPB → **تنظیمات پیش‌فرض نصب**: `proxyIPs` ،`proxyIpMode` ،`fallback` ،`dohUrl`.
  موقع هر نصب اعمال می‌شود؛ تنظیمات تکی هر اکانت بر آن غلبه می‌کند.
- موقع نصب، یک **پسورد پنل** تصادفی تولید و مستقیم داخل KV ورکر (کلید `pwd`) ست می‌شود؛
  پس اولین بازدید `panel_url` مستقیم به صفحه لاگین می‌رود (یوزرنیم = ایمیل اکانت CF).
  پسورد در پنل ادمین با دکمه **پسورد پنل** قابل مشاهده است (اگر ست خودکار شکست بخورد، همان پسورد را در اولین بازدید دستی وارد کنید).

## ۶) تنظیمات تکی و گروهی

دو لایه تنظیمات وجود دارد:

**الف) تنظیمات دیپلوی** (نیازمند redeploy ورکر): `proxyIPs` ،`proxyIpMode` ،`prefixes` ،`fallback` ،`dohUrl`.
تکی (دکمه «تنظیمات دیپلوی» هر ردیف)، گروهی (انتخاب چندتایی → «تنظیمات دیپلوی»)، و پیش‌فرض نصب.
روی اسلات فروخته‌شده لینک را نمی‌کشد (securePath و سکرت‌ها ثابت می‌مانند).

**ب) تنظیمات پنل** (۷۵ کلید runtime خود BPB — بدون redeploy، بدون قطع لینک):
DNS، عبور تحریمی/سرویس‌ها، مسدودسازی‌ها، قوانین سفارشی، فرگمنت، اتصال،
پروکسی زنجیره‌ای، CDN، وارپ، نویز، ساب. دکمه **«تنظیمات پنل»** روی هر ردیف
(حتی اسلات **فروخته‌شده**) ادیتور کامل را باز می‌کند: فرم گروه‌بندی‌شده که نوع
هر فیلد را از مقدار زنده تشخیص می‌دهد + حالت JSON خام. خطاهای اعتبارسنجی خود BPB
(مثلاً DNS نامعتبر) عیناً نمایش داده می‌شود. نسخه گروهی هم از نوار انتخاب انبوه
در دسترس است (patch به‌صورت JSON).

> کلیدهای هویتی (`securePath` ،`UUID` ،پسورد و...) عمداً از ادیتور پنل حذف شده‌اند؛
> ارسال آن‌ها باعث redeploy خودکار ورکر توسط خود BPB می‌شود. چرخش آن‌ها فقط از مسیر
> revoke/انقضا انجام می‌شود تا لینک خریدار بی‌هوا نمیرد.

تب BPB → «تنظیمات» (تکی) یا «تنظیمات گروهی» (bulk روی حداکثر ۵۰ اکانت):
`proxyIPs` ،`proxyIpMode` (`proxyip|direct|none`) ،`fallback` ،`dohUrl`.
کلیدهای ناشناس drop می‌شوند تا با نسخه‌های بعدی BPB سازگار بماند.

## API ادمین (پیشوند `/api/bpb`, نیازمند لاگین)

| متد | مسیر | توضیح |
|-----|------|-------|
| GET | `/api/bpb/accounts` | لیست + شمارنده‌ها (توکن فقط ماسک) |
| POST | `/api/bpb/accounts` | `{ label, apiToken }` |
| GET | `/api/bpb/accounts/:id` | جزئیات یک اکانت |
| POST | `/api/bpb/accounts/:id/install` | verify + KV + deploy |
| POST | `/api/bpb/accounts/:id/revoke` | چرخش سکرت + آزادسازی |
| PUT | `/api/bpb/accounts/:id/settings` | تنظیمات تکی (redeploy) |
| POST | `/api/bpb/accounts/bulk-settings` | `{ ids[], settings }` |
| DELETE | `/api/bpb/accounts/:id` | حذف ورکر + ردیف؛ برای اسلات `sold` باید `{ force: true }` بفرستی |
| GET | `/api/bpb/accounts/:id/token` | نمایش توکن خام (فقط ادمین لاگین‌شده، فقط روی درخواست صریح) |

## ریکاوری: گم شدن VAULT_KEY یا گیر کردن اسلات

- اسلات `sold` عمداً پاک نمی‌شود (لینک خریدار). برای ردیف تستی/خراب، دکمه **حذف** همان ردیف را
  بزن و تأیید اجباری را قبول کن (یا در API `{ force: true }` بفرست).
- اگر `VAULT_KEY` قبلی را گم کرده‌ای، توکن‌های قدیمی (v1) دیگر باز نمی‌شوند و revoke/install
  روی آن اکانت‌ها خطای `vault_decryption_failed` می‌دهد. راه‌حل: دکمه **تعویض توکن** همان
  اکانت → توکن جدید را وارد کن → اکانت دوباره کاملاً قابل مدیریت می‌شود (نصب/revoke/حذف).
  اگر مقدار کلید قدیمی را جایی داری، برگرداندن همان مقدار به سکرت‌ها هم همه‌چیز را درست می‌کند.

> توجه: لیست اکانت‌ها همیشه توکن را ماسک برمی‌گرداند. نمایش کامل توکن فقط با
> دکمه «توکن» روی هر ردیف انجام می‌شود؛ هرکس به پنل ادمین دسترسی دارد می‌تواند
> آن را ببیند، پس دسترسی ادمین را محدود نگه دارید.

## لینک تحویلی به خریدار

برای سرویس‌های BPB فقط **لینک مستقیم ورکر** داده می‌شود (تأییدشده با روتر رسمی `worker.js`؛ مسیر bare یعنی `.../sub` به 404 می‌خورد):
- اصلی (v2rayNG/v2rayN): `https://{worker}.{sub}/{securePath}/sub/normal/xray?app=xray`
- کلش: `.../sub/normal/clash?app=clash` — سینگ‌باکس: `.../sub/normal/sing-box?app=sing-box`
لینک پروکسی `/sub` روی دامین خودمان برای BPB مخفی است
(پیام‌های تکراری هم حذف می‌شوند).

## عیب‌یابی

- `vault_key_required`: `VAULT_KEY` را در Cloudflare ست کنید.
- `provider_auth_failed`: توکن CF نامعتبر است.
- `bpb_no_free_slot`: همه اسلات‌ها sold هستند؛ اکانت جدید نصب کنید.
- جریان‌های Marzban/Marzneshin بدون تغییر باقی می‌مانند (تست‌ها: `npm test`).
